    Context menu

    Concept · 8 frames · pointer and keyboard

    One menu, three doors: the row's ⋯, a right-click anywhere on the row, and the keyboard's context-menu key or Shift+F10. All three open the same object — and it is the same object as the search field's results, because a menu should not be a second dialect: one hairline box, one raised surface, two tiers, never three.

    The ruling

    no new colour · nothing disabled

    destructive — ink, not hue

    Commands rest one tier below the app's full ink. The destructive command is the only one written in full bone, sits behind a 1pt hairline, and is always the last row. No red: the palette has one signal hue and it means “sound is coming out”, so a second one would cost more than the danger it announces.

    omitted, never greyed

    A menu lists what you can do here, not what exists elsewhere. On a playlist you do not own, the destructive row is simply absent — the band goes with it and nothing else moves, because the band is always last. Disabled stays a state for whole controls, not something a row can be.

    The other three rulings are drawn below: “Add to playlist” is a submenu with its own filter (23 lists cannot be one line, and a second panel would leave two surfaces arguing about focus); counts live in the label, never in a header band; and a key hint is only shown for a key that is really bound — today that is Del and nothing else.

    Right-clicking inside a pick acts on the whole pick and does not collapse it — the count in each label is the courtesy. Right-clicking outside a pick selects the row under the pointer first, then opens the menu on it: never both, and never a menu about one row while another row looks picked. No header band states the count twice; the labels already do.

    Twelve rem, hard stop. A verb that does not fit is truncated with an ellipsis, never wrapped onto a second line — a menu row is one line by definition. The destructive band survives the narrowing, because it is structure, not decoration. And the row itself wears nothing: as in M1, the menu is the state.

    M8Closed, and back on the button

    escape returns the keyboard

    Escape pressed · menu gone · focus on the ⋯ keyboard
    1. 2 Harbour Wall 4:05

    Closing puts the keyboard back where it came from — the button that opened the menu, wearing the app's own focus ring. Not the row, not the body: if focus fell to the page you would have to find your way back to the thing you were doing. Tab, a click outside and choosing an item all close it the same way.

    Behaviour

    the part a picture cannot say

    what opens it
    The row's ⋯, a right-click on the row, the context-menu key or Shift+F10. One menu, one position, three doors — including for the ⋯ in Now Playing and the queue.
    what closes it
    Escape (focus returns to the button that opened it), a click outside, Tab, or choosing an item. Escape inside a submenu closes only the submenu and returns the keyboard to its parent row.
    right-click, inside a pick
    Acts on the whole pick. The pick is not collapsed, the labels carry the count, and no header states it twice.
    right-click, outside a pick
    Selects the row under the pointer first, then opens on it. Never a menu about one row while a different row looks picked.
    pointer vs keyboard
    Pointer: nothing is lit until the pointer reaches a row. Keyboard: the first row is lit on open. Only one tier is ever lit at a time — the search menu's rule, unchanged.
    a submenu's field
    While the filter has the keyboard, no row is lit; the arrows move into the list and the field takes them back when the list ends. Escape closes the submenu.
    what is disabled
    Nothing. A verb that cannot apply is absent, not greyed — disabled stays a state for whole controls (a waiting band, a waiting release), never for one row of a menu.
    counts
    In the label when the pick is more than one: “Add 3 tracks to queue”, “Remove 3 tracks from this playlist”. No header band.
    copy link
    One URL per line, which is why a pick says “Copy 3 links” — the count rule applies to it as much as to the destructive command. It sits with the other identity verbs (Go to album, Go to artist), not at the bottom next to the band, and it carries no key hint: nothing is bound to it, and a hint for an unbound key is a lie.
    key hints
    Only for keys that are really bound, right-aligned in mono at the smallest step: Del on the destructive command today. No F2 until renaming exists.

    What gets built

    no new token

    — (nothing added)
    This slice asks the token layer for nothing. The destructive command reuses --color-text and the hairline it already has; the band reuses --color-border; the two lit tiers reuse the search menu's. That is the point of the ruling: it costs the palette nothing.
    the road not taken
    --color-danger plus a hover step, in a warm oxide that cannot be mistaken for the moss accent. Rejected because the app has exactly one signal hue and it means “sound is coming out”; a second would spend the discipline the drag slice just established, and the command is undoable in the product anyway.
    shared with search
    The menu box and both lit tiers moved from .search-menu into .menu, so the field's results and the row's commands are one component. The search sheet keeps its row grammar; only the state classes moved.

    One structural consequence worth writing down: the menu is now a shared object, so a change to its box, its shadow or its lit tiers lands on the search field's results at the same moment it lands here. That is intentional — they were always the same surface.

    Concept · a state board, not a screen. Menus are static specimens, so no row here responds to the pointer. See also drag and drop, the search reference sheet and loading states.
